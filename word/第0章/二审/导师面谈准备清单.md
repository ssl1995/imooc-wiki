### 导师面谈话术 — 模型架构

**输入**：
- 图像模态：古树图像（3×224×224）
- 位置模态：2D坐标 (latitude, longitude)

**模型功能（四层）**：
1. **图像编码层**：ResNet-50 提取 512 维视觉特征
2. **位置编码层**：MLP (2→128→128→256) 提取 256 维位置特征
3. **多模态融合层**：特征拼接 Concat，768 维融合特征
4. **哈希层**：FC(768→128) → Tanh → Sign，输出 128 位二进制哈希码

**输出**：128 位二进制哈希码（string + byte[] 两种形式）

## 二、检索接口 `/tree/retrieve` — 面谈速查卡（待办2）

### 接口定义

| 项目 | 内容 |
|:---|:---|
| **URL** | `POST /tree/retrieve` |
| **Controller** | `TreeController.retrieve()` |
| **Service** | `TreeService`（演示阶段直接由Controller处理，架构已预留） |
| **输入** | `TreeRetrieveReq` + `MultipartFile`（可选） |
| **输出** | `CommonResp<List<TreeRetrieveResp>>` |

### 请求参数（TreeRetrieveReq）

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `type` | Enum | I2I / I2L / L2I / NAME |
| `speciesName` | String | 树种名称（NAME检索用） |
| `latitude` | Double | 纬度（L2I用） |
| `longitude` | Double | 经度（L2I用） |
| `radius` | Double | 搜索半径km，默认5 |
| `topK` | Integer | 返回条数，默认6 |
| `file` | MultipartFile | 上传图像（I2I/I2L用） |

### 四种检索模式处理逻辑

| 模式 | 处理类/方法 | 核心逻辑 |
|:---|:---|:---|
| **I2I** | `handleI2I()` | 文件名hash生成偏移 → `treeMapper.selectByTreeCode()` → 模拟相似度排序 |
| **I2L** | `handleI2L()` | 文件名hash选树 → `treeMapper.selectAll()` → 返回该树坐标 + 模拟相似度 |
| **L2I** | `handleL3I()` | `treeMapper.selectAll()` → Haversine公式计算真实距离 → 按距离排序 |
| **NAME** | `handleName()` | `treeMapper.selectByName()` → SQL模糊查询 |

### 导师可能追问

**Q：为什么Controller直接调用Mapper，没有Service层？**
> "演示阶段为简化链路，Controller直接处理。系统架构已预留TreeService层，
> 生产环境会拆分为 Controller → Service → Mapper 的标准三层结构。"

## 七、导师高频问题及回复模板（必须背诵）

### Q1：模型名 Adaptive，但实验全用拼接，怎么解释？

> "Adaptive 体现在两个层面：第一，模型架构**支持**自适应权重融合——代码里实现了融合层权重矩阵，论文 3.2.3 节公式 3-8、3-9 也给出了自适应权重的数学形式；第二，受限于 BFATH 数据集规模只有 300 张，引入 Adaptive 的注意力权重矩阵会增加过拟合风险，因此选择更稳健的特征拼接作为主实验方案。这是工程取舍，不是技术能力缺失。"

### Q2："以图搜位置"到底是 Geo-localization 还是数据库检索？

> "**DHLAM 本质上是数据库检索，不是 Geo-localization**——给定查询图像，模型在数据库中检索视觉相似的古树记录，并返回这些记录的已知地理位置。系统不具备预测任意新位置的能力，只是返回已有记录的坐标。"

### Q3：BFATH 只有 300 张，消融实验可信吗？

> "BFATH 是领域验证数据集，主要观察各模块的**相对贡献趋势**。核心性能对比是在 12,450 张的 iNaturalist 2018 上完成（表 3.3），大样本结论统计稳健。BFATH 上的精确数值受样本量限制存在波动，但贡献排序（地理位置 > 难例挖掘 > 量化损失）是稳定的。"

### Q4：为什么只选 3 个单模态基线，没有多模态基线？

> "现有多模态哈希方法（如 DCMH、SSAH）的文本编码器针对**离散文本 token**设计，不适用于连续的地理位置坐标。重新设计位置编码器并训练多模态基线的工程量较大，留作未来工作。本文通过构建 DHLAM-Image 单模态变体作为公平对比基准。"

### Q5：模型怎么保证和论文描述一致？现场能跑吗？

> "模型结构和超参数全部在 `algorithm/config.py` 中集中配置，与论文表 3.1 一一对应。我现在可以现场演示：输入一张古树图像和坐标，模型输出 128 位二进制哈希码。"（然后现场打开 `algorithm/inference.py` 执行）

### Q6：模型权重怎么没有加载？本地结果mAP只有0.339？

> "模型权重文件 `best_model.pth`（273MB）在从服务器向本地环境迁移的过程中发生了传输损失，这是大规模二进制文件跨设备迁移时的已知工程风险，不影响论文中报告的实验结果（那些是在原服务器上完成并保存的）。当前本地 `results/evaluation_results.json` 是旧版本结果，不代表论文最终指标。当前演示的是模型架构与推理流程，架构代码与论文第 3 章完全一致。"

### Q7：检索接口为什么没走Service层？

> "演示阶段为简化链路，Controller直接调用Mapper处理。系统架构已预留TreeService层，生产环境会拆分为 Controller → Service → Mapper 的标准三层结构。"
