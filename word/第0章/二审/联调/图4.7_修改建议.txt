================================================================================
图4.7 古树名木检索时序图 — 审查意见与修改建议
================================================================================

说明：本次审查以"时序图必须体现 DHLAM 模型调用"为原则，
      对照论文第3章 DHLAM 架构与实际 TreeController 代码进行。

================================================================================
一、核心结论
================================================================================
图4.7 时序图主体框架正确，但存在 4 类问题：
  ① 2 处类名与实际代码不符
  ② DHLAM 内部流程与论文第3章架构不一致
  ③ 三种检索模式的编码路径差异未体现
  ④ Mapper 查询方法名虚构

================================================================================
二、具体问题清单
================================================================================

【问题1】Controller 类名不符
─────────────────────────────────────────
论文时序图：TreeRetrieveController
实际代码：   TreeController（@RestController + @RequestMapping("tree")）

修改建议：TreeRetrieveController → TreeController

【问题2】Mapper 类名不符
─────────────────────────────────────────
论文时序图：TreeRetrieveMapper
实际代码：   TreeMapper（古树查询）+ ImageInfoMapper（图像关联查询）

修改建议：
  TreeRetrieveMapper → TreeMapper
  或拆分为 TreeMapper + ImageInfoMapper（图像哈希码查询）

【问题3】DHLAM 内部流程与论文第3章架构不一致（重要）
─────────────────────────────────────────
当前时序图 DHLAM 自调用：
  ① 特征提取(ResNet-50 / LocationEncoder)
  ② 多模态融合
  ③ 哈希层生成128位哈希码(FC→Tanh→Sign)

论文第3章 DHLAM 实际架构（3.2节）：
  ├─ 图像特征编码层：ResNet-50 → 512维图像特征向量
  ├─ 位置特征编码层：LocationEncoder(MLP 2→128→128→256) → 256维位置特征
  ├─ 多模态融合层：特征拼接(Concat) → 768维融合特征
  └─ 哈希层：FC(768→128) → Tanh → Sign → 128位二进制哈希码

当前时序图将"特征提取"和"位置编码"画在同一个自调用框中，
模糊了图像/位置两个独立编码器。应拆分为两个并行的自调用步骤。

修改建议：
  DHLAM 内部流程拆分为 4 个清晰的自调用步骤：
    Step 1: ImageEncoder(ResNet-50) → 512维图像特征
    Step 2: LocationEncoder(MLP) → 256维位置特征  
    Step 3: 多模态融合(Concat) → 768维融合特征
    Step 4: 哈希层(FC→Tanh→Sign) → 128位哈希码

【问题4】三种检索模式编码路径差异未体现（重要）
─────────────────────────────────────────
当前时序图底部 note 说"三种检索模式共享同一流程"，
但实际上三种模式的 DHLAM 输入和编码路径不同：

  I2I（图像→图像）：
    输入：Query图像
    编码：ImageEncoder → 512维 → 哈希层 → 128位图像哈希码
    查询：与 image 表 hash_bits 汉明距离计算，返回相似图像

  I2L（图像→位置）：
    输入：Query图像
    编码：ImageEncoder + LocationEncoder → 融合 → 哈希层 → 128位融合哈希码
    查询：检索数据库中视觉相似古树的已知地理位置

  L2I（位置→图像）：
    输入：Query坐标(lat, lon)
    编码：LocationEncoder → 256维 → 哈希层 → 128位位置哈希码
    查询：检索该坐标附近的古树图像

修改建议：
  时序图以 I2I 为主流程（最完整的图像编码→哈希→检索链路），
  在底部 note 中补充说明：
    "I2L 在图像编码基础上增加位置编码与融合；
     L2I 仅使用位置编码生成哈希码"

【问题5】Mapper 查询方法名虚构
─────────────────────────────────────────
论文时序图：Mapper: selectByHashCode(hash)
实际代码：   无此方法。演示阶段用 treeMapper.selectAll() + 内存排序。
            理想架构应为：查询 image 表 hash_bits，计算汉明距离。

修改建议：
  因时序图必须走 DHLAM 模型，此方法名可保留为理想化设计，
  但建议改为更准确的描述，如：
    "查询 image 表 hash_bits 并计算汉明距离"
  或具体方法名：selectByHammingDistance(hashBits, topK)

================================================================================
三、时序图重构建议
================================================================================

【参与者调整】
─────────────────────────────────────────
  TreeRetrieveController → TreeController
  TreeRetrieveMapper → TreeMapper（+ ImageInfoMapper）
  其余参与者保留

【DHLAM 内部流程细化】
─────────────────────────────────────────
  将当前单一的 "DHLAM -> DHLAM: 特征提取/融合/哈希" 拆分为：

  Service -> DHLAM: 调用模型推理(queryImage / queryCoord)
  activate DHLAM

  DHLAM -> DHLAM: ImageEncoder(ResNet-50) 提取512维图像特征
  DHLAM -> DHLAM: LocationEncoder(MLP) 编码256维位置特征
  DHLAM -> DHLAM: 多模态融合(Concat) 生成768维融合特征
  DHLAM -> DHLAM: 哈希层(FC→Tanh→Sign) 生成128位二进制哈希码

  DHLAM --> Service: 返回 hashCode + hashBits
  deactivate DHLAM

【数据库查询流程调整】
─────────────────────────────────────────
  Service -> Mapper: 查询 image 表 hash_bits 计算汉明距离
  Mapper -> DB: SELECT * FROM image WHERE is_delete=0
  DB --> Mapper: 返回全部图像哈希记录
  Mapper --> Service: 返回 List<Image>
  Service -> Service: 逐条计算汉明距离并排序(Top-K)

【底部 note 调整】
─────────────────────────────────────────
  当前："三种检索模式共享同一流程"
  改为："I2I为主流程（图像编码→哈希→汉明距离检索）；
         I2L增加位置编码与融合；L2I仅使用位置编码"

四、文字描述同步修改
================================================================================

原文：
  "请求经TreeRetrieveController路由至ITreeRetrieveService。
   Service层调用DHLAM模型服务，由模型完成图像/位置特征提取、
   多模态融合及128位哈希码生成，返回哈希码后通过TreeRetrieveMapper
   执行数据库哈希码相似度查询..."

修改为：
  "请求经 TreeController 路由至 TreeService。Service 层调用 DHLAM 模型服务：
   图像检索(I2I)由 ImageEncoder(ResNet-50)提取512维图像特征，经哈希层
   (FC→Tanh→Sign)生成128位二进制哈希码；位置检索(L2I)由 LocationEncoder
   编码256维位置特征后生成哈希码；图像到位置检索(I2L)则融合图像与位置
   双模态特征后生成哈希码。返回哈希码后通过 TreeMapper 查询 image 表
   hash_bits 字段，计算汉明距离并按距离排序取 Top-K 结果。"

五、当前演示阶段与理想架构的衔接说明
================================================================================

当前代码中 TreeController.retrieve() 演示阶段使用 HashRetrieveService
基于文件名生成确定性伪哈希码，未接入真实 DHLAM 模型。

时序图作为系统设计文档，应体现理想架构（含 DHLAM 模型调用），
建议在论文文字或时序图 note 中增加说明：

  "当前演示阶段采用 HashRetrieveService 基于文件名生成确定性伪哈希码
   替代 DHLAM 模型推理，系统架构已预留 DHLAM 模型接入接口，
   生产环境可直接替换为真实模型调用。"
