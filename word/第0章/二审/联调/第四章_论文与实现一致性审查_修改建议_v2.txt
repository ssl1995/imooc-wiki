【必须修改】ER图四个实体字段均严重缺失，需与实际SQL对齐：

1. Tree 实体
   当前ER图仅5个字段：树种名称、树龄、树高、纬度、经度
   应补充为12个：id(PK)、tree_code、name、树种名称、树龄、树高、

2. Image 实体
   当前ER图5个字段：tree_id(FK)、存储路径、hash_code、hash_bits
   应补充为8个：id(PK)、tree_id(FK)、存储路径、hash_code、hash_bits、
                 是否逻辑删除、创建时间、更新时间

   当前ER图4个字段：id(PK)、用户名、密码、个人描述
   应补充为8个：id(PK)、login_name、name、password、age、desc、
                 per_role_id、last_login_time

4. Role 实体
   当前ER图3个字段：id(PK)、角色名称、权限描述
   应补充为6个：id(PK)、角色名称、权限描述、是否逻辑删除、创建时间、更新时间

   当前ER图中 User "1--N" MaintainImage "N--1" Image 的关系无业务支撑，
   建议删除以简化ER图，保持与文字描述一致。

三、时序图与实际代码不一致
================================================================================

【必须修改】图4.7 古树名木检索时序图
─────────────────────────────────────────
论文描述：
  前端 POST /tree/retrieve
    → TreeRetrieveController
    → ITreeRetrieveService
    → DHLAM模型（特征提取→多模态融合→哈希层生成128位哈希码）
    → TreeRetrieveMapper
    → MySQL（哈希码相似度查询）

实际代码：
  前端 POST /tree/retrieve
    → TreeController.retrieve()        【类名不符】
    → 【无 Service 层，Controller 直接处理】 【缺少Service层】
    → HashRetrieveService（演示阶段伪哈希生成） 【替代DHLAM】
    → TreeMapper / ImageInfoMapper     【Mapper名不符】
    → MySQL（SQL查询，非哈希码相似度） 【查询方式不符】

修改建议：
  (1) Controller 名称：TreeRetrieveController → TreeController
  (2) 删除 ITreeRetrieveService 层（或增加 TreeService 做薄转发，
      但答辩前新增 Service 层改动意义不大，建议直接删除时序图中 Service 层）
  (3) Mapper 名称：TreeRetrieveMapper → TreeMapper（+ ImageInfoMapper）
  (4) DHLAM模型：保留（作为架构设计说明），但增加注释"演示阶段由
      HashRetrieveService 基于文件名生成确定性伪哈希码替代"
  (5) 文字描述同步修改：
      "请求经 TreeController 路由，由 HashRetrieveService 生成哈希码
       （演示阶段为伪哈希，生产环境接入DHLAM模型），
       通过 TreeMapper/ImageInfoMapper 查询数据库..."

【必须修改】图4.5 用户信息时序图
─────────────────────────────────────────
论文描述：
  UserPage → Controller: 调用 /user/getUserInfo/{userId} (GET)
  Controller → Service: getUserInfoByUserId(userId)
  Service → Mapper: selectUserInfoByUserId(userId)

实际代码：
  • 无 /user/getUserInfo/{userId} 接口
  • 实际接口：/user/list（分页查询用户列表，带 keyword 参数）
  • Service 层确实存在（UserServiceImpl.list()）
  • Mapper：UserMapper.selectByExample（MyBatis Generator生成）

修改建议：
  (1) 接口路径：/user/getUserInfo/{userId} → /user/list
  (2) Service 方法：getUserInfoByUserId() → list()
  (3) Mapper 方法：selectUserInfoByUserId() → selectByExample
  (4) 或【更简洁方案】：直接删除图4.5，因为用户信息管理非核心功能，
      且已有图4.6页面截图佐证，删除时序图不影响论文完整性。

【建议论文修改】4.1.1节 密码加密算法
─────────────────────────────────────────
论文原文："密码通过bcrypt哈希算法加密存储"
实际代码：UserController 第52行使用 DigestUtils.md5DigestAsHex 进行 MD5 加密

建议：论文改为 "密码通过 MD5 哈希算法加盐后不可逆加密存储"，
      与前端 hexMd5(password + "!@#QWERT") 逻辑对应。

【建议论文修改】4.1.1节 用户名校验规则
─────────────────────────────────────────
论文原文："用户名校验规则为8-12位，包含数字、区分大小写字母与符号"

建议：简化或删除该校验规则描述，与实际系统保持一致。

【建议论文修改】4.1.1节 昵称长度限制
─────────────────────────────────────────
论文原文："昵称长度应在8~16个字符范围内"

            无"哈希索引管理"和"检索日志审计"模块代码

建议：删除"哈希索引管理"和"检索日志审计"两个模块描述，

  GET  /user/logout/{token} — 退出登录

【HashRetrieveService（演示阶段替代 DHLAM）】
  generate(filename)  → 基于文件名生成确定性128位伪哈希码
  offset(filename, mod) → 基于文件名hashCode的取模偏移
  similarity(filename, min, max) → 基于文件名hashCode的相似度
